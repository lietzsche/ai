# 체감 점검 (feel)

눈에 띄는 버그는 아니지만 써 보면 느리거나 어색한 문제를 다룬다. 세 세션이 역할을 나눈다. 사용자의 언어로 대화한다.

| 세션 | 역할 | 수정 권한 |
| --- | --- | --- |
| **메인(총괄)** | 범위 정하기, 두 세션 지시, 결과 종합, 수정 구현, 최종 판정 | 있음 |
| **검수** | 원인 찾기(코드·데이터 흐름·네트워크·렌더링·I/O), 수정 diff 검토 | 없음(읽기·실행만) |
| **평가** | 사용자 관점 체감 측정과 점수, 수정 전후 비교, 회귀 판정 | 없음(읽기·실행만) |

검수와 평가는 서로의 결과를 보지 않고 독립적으로 작업한다. 원인 분석(검수)과 체감 판정(평가)을 분리해, 고친 사람이 스스로 "좋아졌다"고 판정하는 일을 막는다.

## 입력과 시작하기

- 호출 인자로 받은 대상(화면, 명령, 엔드포인트, 사용자 흐름, 증상)과 대화 맥락을 읽는다. 인자가 없으면 최근 변경된 부분(`git log`, `git diff`)이나 주요 사용자 흐름을 후보로 제시한다.
- 질문하기 전에 대상 프로젝트를 직접 조사해 다음을 파악한다.
  - **프로젝트 종류**: 웹 프런트엔드, 모바일 앱, 데스크톱 앱, CLI, 백엔드·API, 게임·그래픽, 데이터 처리 등(여러 개일 수 있다)
  - **실행·빌드·테스트 명령**: `README`, 패키지·빌드 설정(`package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `build.gradle`, `Makefile` 등), CI 설정
  - **프로젝트 규칙**: `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING` 등의 커밋·브랜치·검증 규칙
  - **사용 가능한 측정 도구**: 브라우저 자동화·DevTools, 프로파일러, 벤치마크 도구, 로그
- 대상이나 증상이 전혀 특정되지 않을 때만 한 번에 한 질문씩 묻는다. 선택지를 제시할 때는 현재 저장소에 `skills/grill-me/SKILL.md`가 있으면 그 선택형 질문 UI 지침을 따르고, 없으면 호스트의 질문 도구(Claude Code `AskUserQuestion`, Codex `request_user_input`)를 쓰거나 추천안을 맨 앞에 둔 번호 목록으로 묻는다.

## 실행 단계

### 1단계 — 범위와 기준 정하기 (메인)

- 점검할 **대상 흐름**을 1~3개로 좁힌다. 예: "첫 화면 진입", "목록에서 상세로 이동", "검색어 입력 후 결과 표시", "`mytool build` 실행", "주문 생성 API 호출".
- 흐름마다 **체감 지표**를 정한다. 프로젝트 종류에 맞는 것을 고르고, 측정 가능한 것을 우선한다.

  | 관점 | 웹·모바일·데스크톱 UI | CLI·백엔드·API·데이터 처리 |
  | --- | --- | --- |
  | 로딩 | LCP·첫 콘텐츠 표시, 앱 시작 시간, 데이터 도착까지 시간, 요청 수·크기·폭포 구조, 번들·바이너리 크기 | 시작(콜드 스타트) 시간, 첫 출력까지 시간, 전체 소요 시간, p50·p95 응답 시간, 처리량 |
  | 반응 | INP·입력 지연, 탭·클릭 후 피드백까지 시간, 메인 스레드 긴 작업, 프레임 드롭(60fps 미달) | 진행 표시 없이 멈춘 듯한 구간, 인터럽트(Ctrl+C) 반응, 타임아웃 |
  | 안정성 | CLS·레이아웃 밀림, 깜빡임, 스켈레톤·빈 화면 노출 시간 | 응답 시간 편차, 간헐적 지연, 메모리·CPU 급증 |
  | 경험 | 중복 요청, 불필요한 재렌더, 낙관적 갱신 부재, 스크롤·전환 끊김, 포커스·스크롤 위치 유실 | N+1 쿼리, 불필요한 I/O·재계산, 캐시 부재, 출력 과다·부족, 이해하기 어려운 오류 메시지 |

- **측정 환경**을 정한다(로컬 개발 모드, 프로덕션·릴리스 빌드, 스테이징·배포 주소, 실기기·에뮬레이터, 데이터 크기, 네트워크·CPU 스로틀링 여부). 가능하면 실제 사용과 가까운 릴리스 빌드로 측정한다. 운영 환경에 부하를 주거나 데이터를 바꾸는 측정은 사용자 승인 없이 하지 않는다.

### 2단계 — 독립 점검 (검수 ∥ 평가, 병렬)

메인은 두 세션에 다음을 전달해 **동시에** 시작한다.

- **검수 세션 지시**: 대상 흐름, 증상, 관련 코드 경로 후보, 실행 방법. 할 일은 원인 후보를 찾고 근거(파일:줄, 요청·쿼리 로그, 프로파일 결과)를 붙이는 것. 각 발견에 `영향(높음/중간/낮음)`, `확신도`, `수정 방향`을 단다. 파일을 수정하지 않는다.
- **평가 세션 지시**: 대상 흐름, 체감 지표, 측정 환경, 실행 방법. 할 일은 기준선(Baseline)을 측정하고 흐름마다 체감 점수(1~5)와 근거 수치를 기록하는 것. 같은 측정을 최소 3회 반복해 중앙값을 쓰고, 측정 명령·조건을 함께 남겨 4단계에서 그대로 재현할 수 있게 한다. 원인 추측보다 "사용자가 무엇을 겪는가"를 기록한다. 파일을 수정하지 않는다.

### 3단계 — 종합과 수정 (메인)

- 검수 발견과 평가 수치를 맞춰 본다. 평가에서 나쁜 지표가 검수 발견으로 설명되는지, 설명되지 않는 체감 문제가 남는지 확인한다.
- `체감 영향 ÷ 수정 비용` 순으로 수정 대상을 고르고, 근거가 약하거나 효과가 미미한 항목은 보류 목록에 남긴다.
- 메인이 수정을 구현한다. 한 번에 하나의 원인 단위로 고쳐 효과를 구분할 수 있게 한다. 프로젝트의 기존 테스트·린트·타입 검사·빌드를 통과시킨다.

### 4단계 — 교차 검증 (검수 ∥ 평가, 병렬)

- **검수 세션**: 수정 diff를 검토한다. 원인이 실제로 해소됐는지, 기능 회귀·엣지 케이스(빈 데이터, 대용량 데이터, 느린 네트워크, 작은 화면, 오류 상태, 동시 요청)·접근성 손상이 없는지 확인하고 `통과 / 수정 필요`를 낸다.
- **평가 세션**: 2단계와 같은 환경·절차로 다시 측정해 전후 비교표를 만든다. 개선 폭이 측정 오차 범위 안이면 "개선 불확실"로 판정한다. 다른 흐름의 회귀도 확인한다.

### 5단계 — 판정과 반복 (메인)

- 두 세션이 모두 통과하면 종료한다.
- 하나라도 `수정 필요`나 회귀가 있으면 3단계로 돌아간다. **최대 2회** 반복하고, 그래도 해결되지 않으면 현재 상태와 남은 문제를 보고하고 멈춘다.

## 환경별 실행 방법

- **Claude Code**: `Agent` 도구로 검수·평가 서브에이전트를 만든다. 2단계와 4단계에서는 두 호출을 한 턴에 병렬로 보낸다. 각 지시에 역할, 대상, 실행 방법, 측정 환경, 산출물 형식, "파일 수정 금지"를 명시한다. 4단계에서 같은 서브에이전트를 이어 쓸 수 있으면(`SendMessage`) 이어 쓰되, 평가 세션에는 검수 결과를 넘기지 않는다. 브라우저 측정 도구(Chrome DevTools MCP, Claude in Chrome 등)나 `web-perf` 같은 성능 측정 스킬이 있으면 평가 세션이 사용한다.
- **Codex**: 서브에이전트·멀티에이전트 도구가 있으면 같은 방식으로 위임한다. 없으면 아래 단일 세션 대체 동작을 쓴다.
- **단일 세션 대체 동작**: 서브에이전트를 만들 수 없으면 메인이 역할을 순서대로 바꿔 수행한다(`평가(기준선) → 검수 → 수정 → 검수(diff) → 평가(재측정)`). 평가 기준선은 검수보다 **먼저** 기록해 원인 추측이 측정에 영향을 주지 않게 한다. 보고에 단일 세션으로 수행했음을 밝힌다.
- **측정 도구 대체**: 전용 측정 도구가 없으면 프로젝트 종류에 맞는 범용 수단으로 대체한다.
  - 웹: 빌드 산출물 크기, 네트워크 요청 목록, `curl -w` 타이밍, 코드 정적 분석
  - CLI·스크립트: `time`·`hyperfine`·PowerShell `Measure-Command`로 반복 실행 시간 측정
  - 백엔드·API: 반복 요청 타이밍, 서버·쿼리 로그, 언어별 프로파일러(`cProfile`, `pprof`, `--prof` 등)
  - 모바일·데스크톱: 시작 로그 타임스탬프, 플랫폼 프로파일러 사용 가능 여부 확인
  - 실측하지 못한 지표는 "미측정"으로 표시하고 추정치를 측정값처럼 보고하지 않는다.

## 결과 보고

대화에 다음을 간결하게 보고한다.

1. **결론**: 무엇이 체감상 얼마나 좋아졌는지 한두 문장
2. **전후 비교표**: 흐름 × 지표, 기준선 → 수정 후, 체감 점수 변화
3. **수정 내역**: 원인, 고친 파일, 근거
4. **보류·남은 문제**: 고치지 않은 발견과 이유, 미측정 지표
5. **수행 방식**: 3세션 / 단일 세션 대체 여부, 측정 환경

수정이 저장소에 반영됐으면 대상 프로젝트의 커밋·푸시 규칙(`AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING` 등)을 따르고, 규칙이 없으면 커밋 여부를 사용자에게 맡긴다. 승인 범위를 넘는 작업(배포, 운영 데이터 변경, 의존성 대규모 교체, 운영 환경 부하 테스트)은 제안만 하고 실행하지 않는다.

## 참고

원래 특정 웹 프로젝트용으로 만든 `feel` 스킬을 프로젝트 종류와 상관없이 쓰도록 일반화했다. 웹 지표(LCP, INP, CLS)는 [web.dev Core Web Vitals](https://web.dev/articles/vitals) 정의를 따른다.
