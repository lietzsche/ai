04 · handsoff는 정확히 무엇인가?

동명이므로 이름만으로는 특정할 수 없습니다.

개발 스킬 문맥에서는 btseytlin/ultrapack의 handsoff가 유력한 후보입니다. 별도로 altalt-org/HandsOff라는 Android 자동화 프로젝트도 확인됐습니다. 사용자가 보았던 링크는 없어 둘 다 설명합니다. 어느 쪽도 이번에 설치하거나 실행하지 않았습니다.

A. Ultrapack handsoff — 중간 질문을 줄이는 운영 규약

제작 계정은 btseytlin입니다. 단독 자동화 엔진보다는 Ultrapack의 여러 단계가 공유하는 규칙입니다. 사용자가 처음 방향을 정한 뒤 매 단계의 승인 질문을 줄이고, 자동 결정과 보류 사항을 마지막에 검토하게 합니다. Ultrapack README

원문에서 확인한 핵심 동작
  • 작업 파일의 **Mode:** hands-off가 활성화 기준입니다. 헤더가 없거나 interactive이면 일반 흐름을 따릅니다.
  • 별도 브랜치와 worktree를 사용하고, 이를 만들지 못하면 보류합니다. 강제 푸시·파괴적 Git 작업·훅 우회는 금지합니다.
  • 계획 승인 대기는 생략할 수 있지만 자동 선택은 Hands-off decisions에 이유와 함께 기록합니다.
  • 근거 없는 필수 값이나 모호한 선택은 지어내지 않고 Deferred (needs user input)에 남깁니다.
  • 원격 푸시는 자동 실행하지 않습니다. 관측하지 못한 실제 목표는 완료로 표시하지 않고 validating 상태로 남깁니다.
  • 마지막에는 결정·보류 목록을 제시하고 사용자 응답을 받은 뒤 마무리 선택지를 제공합니다.

즉, 질문 횟수를 줄여도 권한을 확대하지 않는 설계입니다. handsoff 원문

공식 README에 있는 설치·호출 예시

아래는 조사용 예시입니다. 실행하지 않았습니다. 개별 handsoff 파일만 추가하기보다 전체 워크플로 안에서 쓰는 구조를 이해하는 편이 좋습니다.

설계부터 문서 갱신까지 이어지는 진입점은 make입니다. task 파일을 새 세션의 재개 근거로 씁니다. 공식 설치 안내

우리 환경과 비교한 해석: 작업별 결정 로그와 보류 로그는 make-plan·teamwork에도 참고할 만합니다. 다만 현재 저장소 규칙은 작업 완료 후 커밋·푸시를 요구하고, Ultrapack 규약은 자동 푸시를 하지 않도록 하므로 그대로 복사하면 충돌합니다. 운영 규칙의 우선순위를 먼저 정해야 합니다. 스킬의 문장만으로 지속 실행이나 권한 우회가 보장되는 것도 아닙니다.

B. altalt-org/HandsOff — AI에게 Android 기기를 제공

이 프로젝트는 AWS에서 Android 기기를 실행하고, Tailscale로 연결한 뒤 MCP를 통해 탭·스와이프·텍스트 입력·앱 설치·스크린샷 같은 조작을 제공한다고 설명합니다. ReDroid, 브라우저 화면 미러링, 기기 제어용 MCP 서버를 함께 사용합니다. 공식 저장소

AWS 계정과 인증된 CLI, Tailscale, MCP를 지원하는 에이전트 환경이 필요합니다. README의 설치 흐름에는 클라우드 인스턴스 생성과 배포가 포함됩니다. 이번에는 원격 기기나 계정을 만들지 않았습니다. 공개 소스는 확인했지만 명시적 오픈소스 라이선스는 확정하지 못했습니다.

05 · 지금의 구성에서 활용하기

  1. 문서 품질 개선: doc-coauthoring의 독자 검증을 먼저 참고하고, 파일 형식에 따라 docx·pdf·pptx·xlsx를 살펴보세요.
  2. 개발 스킬 개선: Matt의 작은 스킬 구성과 Superpowers의 단계별 검증을 현재 스킬과 비교하세요. 전체 도입보다 중복과 누락을 먼저 찾는 편이 낫습니다.
  3. 질문 횟수 줄이기: handsoff의 결정·보류 로그를 참고할 수 있습니다. 무응답을 승인으로 간주하지 않는 현재 인터뷰 규칙은 별도로 유지해야 합니다.
  4. 라이선스 관리: 공개 저장소에서 가져올 때 URL·커밋·LICENSE를 함께 기록하세요. 설치된 동명 사본과 공개 버전이 같은 배포 조건이라고 가정하지 마세요.
